# Git Commit

按实际 diff 将改动拆成可独立理解和回滚的功能提交；不要按文件机械拆分。全部提交完成后只推送一次。

## 流程

1. 运行 `git status -sb`。若工作区干净，告知“工作区干净，无需提交”并结束。若存在冲突、未完成的 merge/rebase/cherry-pick 或 detached HEAD，说明情况并停止。
2. 运行 `git diff`、`git diff --staged`，并读取未跟踪文件。所有分组和描述必须来自实际改动，禁止臆测。
3. 按功能分组：
   - 同一功能的实现、测试、调用方适配、锁文件和直接相关文档通常放在一起。
   - 互不相关的功能、修复、重构、格式或工具改动分别提交。
   - 同一文件包含多个功能时使用 `git add -p -- <文件>`。
   - 无法可靠拆分时询问用户，不得为拆分而修改或丢弃代码。
4. 提交前展示完整计划：每个提交的信息、文件或代码片段及顺序。
5. 逐组执行：

```bash
git add -- <当前功能的文件>
git diff --staged
git commit -m "<提交信息>"
git status --short
```

不要使用 `git add .`。每次提交前确认暂存区只包含当前功能，且没有密钥、令牌或密码。

6. 全部提交后运行 `git status -sb` 和 `git log --oneline -n <本次提交数>`，确认无遗漏后执行：

```bash
git push origin <当前分支>
```

分支名必须从 Git 状态读取，不得猜测。

## 提交信息

格式：

```text
<类型>: <中文简短描述>
```

类型：`feat` 新功能、`fix` 修复、`docs` 文档、`style` 格式、`perf` 性能、`test` 测试、`refactor` 重构、`revert` 回滚、`chore` 构建/工具/依赖。

示例：

```text
feat: 新增差旅申请审批功能
fix: 修复订单金额计算错误
refactor: 抽取公共请求逻辑
```

描述必须准确概括当前提交，不得包含 diff 中不存在的内容或 AI 生成标识。

## 异常处理

- 提交失败：保留现场、展示错误并停止；不得使用 `--no-verify`。
- 推送被拒绝：不要 pull、merge、rebase 或强制推送；告知“请手动解决冲突，并重新执行 `git push`”。
- 发现敏感信息：不提交、不推送，只指出涉及文件，不展示敏感值。
- 禁止使用 `git reset --hard`、丢弃工作区内容、修改已有提交或强制推送。

完成后汇总当前分支、提交数量、每个提交的短哈希与信息、推送目标及剩余未提交改动。
